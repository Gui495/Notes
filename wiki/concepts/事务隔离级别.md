事务隔离级别是数据库对「多个并发事务之间，一个事务能看到另一个事务的哪些中间状态」所给出的分级契约，它同时决定了读操作要不要加锁、以及写操作要锁住多大范围。

> 📌 来源性质：本页无 raw 素材，依据外部资料编写，待有 raw 素材时再收编。

MySQL 的 InnoDB 提供 SQL:1992 标准的全部四个级别，默认值是 REPEATABLE READ。要注意这里的两层含义必须分开：级别既是对「可见性」的承诺（靠多版本与快照实现），也是对「加锁范围」的承诺（靠记录锁、间隙锁实现）。只记住「RR 能防幻读」这种结论会误判，因为同一级别下普通 SELECT 与 `SELECT ... FOR UPDATE` 走的是两套完全不同的机制。

## 并发读的四种异常

四种异常按「被破坏的是什么」可以排成一条线：脏读破坏的是「只读已提交」，不可重复读破坏的是「单行值的稳定」，幻读破坏的是「行集合的稳定」，更新丢失破坏的是「写操作的排他」。前三种是读侧问题，第四种是写侧问题，混为一谈会导致选错级别。

| 异常 | 现象 | 触发条件 |
| --- | --- | --- |
| 脏读 dirty read | 读到另一个事务尚未提交的行 | 读不加锁，且允许看到未提交版本（RU） |
| 不可重复读 nonrepeatable read | 同一事务内两次读同一行，值不同 | 两次读之间别的事务提交了该行的修改 |
| 幻读 phantom | 同一事务内同一查询两次执行，返回的行集合不同 | 两次读之间别的事务插入（或删除）了符合条件的行 |
| 更新丢失 lost update | 两个事务基于同一个旧值各自计算并写回，后写覆盖前写 | 读—算—写之间没有对目标行加独占锁 |

幻读与不可重复读的判据在「行集合 vs 单行」：官方对幻读的表述是「the same query executed at different times within the same transaction returns different sets of rows」。因为问题从「某一行变了」升级为「多出了行」，单条记录锁已经拦不住，必须锁住「记录之间的空隙」才可能防住，这正是间隙锁存在的理由。

## 四个隔离级别各自阻止什么

下表按「快照的时效」与「加锁的方式」两列来读，比单纯背「能否防幻读」更接近真相：

| 级别 | 脏读 | 不可重复读 | 幻读 | 更新丢失 | 快照与加锁要点 |
| --- | --- | --- | --- | --- | --- |
| READ UNCOMMITTED | 不阻止 | 不阻止 | 不阻止 | 不阻止 | 普通 SELECT 不加锁，可能读到更早版本的行 |
| READ COMMITTED | 阻止 | 不阻止 | 不阻止 | 不阻止 | 每条 SELECT 新建一次快照；写只加记录锁，不放间隙锁 |
| REPEATABLE READ | 阻止 | 阻止 | 部分阻止 | 不阻止 | 快照在事务首次读时建立；写用 next-key 锁覆盖扫描范围 |
| SERIALIZABLE | 阻止 | 阻止 | 阻止 | 阻止（读也持锁） | 普通 SELECT 被隐式转成共享锁读 |

**READ UNCOMMITTED** 在 InnoDB 里并不是「完全无控制」，它只是允许普通 SELECT 用上比最新提交版本更早的版本，官方措辞是「This is also called a dirty read」，其余行为与 READ COMMITTED 相同。它几乎只用于「看个大概」的统计场景，任何有业务判断的读取都不该用它。

**READ COMMITTED** 的关键不是「阻止脏读」，而是「每次 SELECT 都重新取快照」。因此同一事务里两次查询之间，别的事务提交的修改会被看见——这既是它不阻止不可重复读的原因，也是它被很多高并发系统选为默认级别的原因（快照短、undo 压力小）。代价是写侧的间隙锁被显式禁用：只保留给外键约束检查与重复键检查，所以范围插入带来的幻读在 RC 下是允许发生的。官方原文明确了这一点：「Only row-based binary logging is supported with the READ COMMITTED isolation level.」——这一条把它与复制安全绑在了一起，见后文。

**REPEATABLE READ（InnoDB 默认）** 的承诺是「同一事务内的普通 SELECT 看到同一个快照」，快照在事务第一次读时建立，之后的普通 SELECT 都复用它。它不阻止的是写侧的竞态：普通 SELECT 不加锁，所以「先读出来、在应用层算、再写回去」这种读—改—写在 RR 下依然会互相覆盖，这就是更新丢失必须靠 `FOR UPDATE` 或 `UPDATE ... SET v = v - x` 这类原子写法来解决的原因。另一条官方告警常被忽略：在 RR 下**不建议在同一个事务里混用锁定读与非锁定读**，因为非锁定 SELECT 走 read view（不含本事务之前的其他未提交事务、且不含本事务自己的写），而锁定语句读最新状态，两者拼在一起的结果「hard to interpret」。

**SERIALIZABLE** 在上述基础上再进一步：当 `autocommit` 关闭时，InnoDB 把所有普通 SELECT 隐式转成 `SELECT ... FOR SHARE`，读取也持共享锁，于是读—写之间无法交错。`autocommit` 开启时每条 SELECT 自成事务，此时它仍可作不阻塞他人的一致性读；也就是说「SERIALIZABLE 会让读阻塞写」这个印象只在关闭 autocommit（或显式开事务）时成立。

## 快照读与当前读的分工

MVCC 由两个零件组成：**undo log 存旧版本**，**Read View 决定可见性**。官方对 undo log 的作用给了一句非常适合当定义的话：它记录「how to undo the most recent change to a row」，并且「if another transaction needs to see the original data as part of a consistent read, the unmodified data is retrieved from the undo log records」。也就是说 undo log 不只是回滚用的，它同时是 MVCC 的「历史版本仓库」——这是理解 RR 为什么能读到旧值的唯一正确入口。

Read View 是「判断某个版本对当前事务是否可见」的快照判据：REPEATABLE READ 下整个事务只建一次，READ COMMITTED 下每条语句建一次。这里即出现两种读的分界：

| 读法 | 语句 | 是否加锁 | 读到什么 |
| --- | --- | --- | --- |
| 快照读（一致性读） | 普通 `SELECT` | 否 | 按 Read View 可见的那个版本，可能是旧值 |
| 当前读 | `SELECT ... FOR UPDATE`、`SELECT ... FOR SHARE`、`UPDATE`、`DELETE`、`INSERT` | 是 | 最新已提交版本，并对其加锁 |

一致性读还有几条容易踩的边界，官方专门列出：它对本事务自己更早语句做过的修改是可见的（不是纯快照）；`DROP TABLE` 之后一致性读会失效；对「复制原表再删除原表」方式的 `ALTER TABLE` 也失效，会报 `ER_TABLE_DEF_CHANGED`「Table definition has changed, please retry transaction」。此外 `INSERT ... SELECT`、`UPDATE ... (SELECT)`、`CREATE TABLE ... SELECT` 在没有写 `FOR UPDATE`/`FOR SHARE` 时，InnoDB 会施加更强的锁，其 SELECT 部分实际按 READ COMMITTED 的规则处理。

当前读的两种写法中，`SELECT ... FOR UPDATE` 加排他锁（写意向）、`SELECT ... FOR SHARE` 加共享锁；表级意向锁 IS/IX 随之加上，用来阻塞 `LOCK TABLES ... WRITE` 这类全表请求，而不阻塞行级操作。8.0 文档统一写作 `FOR SHARE`，旧写法 `LOCK IN SHARE MODE` 在 8.0 中是否已标记弃用，本页未核到原文（待核）。Read View 的内部字段名（活跃事务集合、上下界阈值等）属于实现细节，本页只讲语义、不写字段名（待核）。

## RR 下的幻读：间隙锁解决了什么、没解决什么

先把锁的层次摆清楚。InnoDB 的行锁加在**索引记录**上，无索引时会落到隐藏的聚簇索引上。**记录锁**锁单条索引记录；**间隙锁（gap lock）** 锁两条索引记录之间的空隙；**next-key lock** 是两者的组合——记录锁加「该记录之前的间隙」。官方给的区间感很实用：若索引值为 10、11、13、20，各记录的 next-key 锁区间为 (−∞,10]、(10,11]、(11,13]、(13,20]、(20,+∞)，最后一段锁的是大于最大值的间隙（supremum 伪记录之前）。官方举例：`SELECT c1 FROM t WHERE c1 BETWEEN 10 AND 20 FOR UPDATE` 会阻止别人插入 15，这正是「用锁死空隙来防幻读」的机制表达。

间隙锁有两个反直觉的性质，决定了很多「以为防住了其实没防住」的现场：其一，它纯粹是**抑制性**的，只阻止插入，S 与 X 类型的间隙锁并不互斥、可以共存；其二，**用唯一索引定位唯一行时不需要间隙锁**——官方例子是 `SELECT * FROM child WHERE id = 100`，`id` 唯一时只加记录锁，不锁前面的间隙。而 `id` 非唯一或没有索引时，则会顺带锁住它前面的间隙。

由此可以回答「RR 下幻读为什么只是部分被解决」。缺口有三类：**一是唯一索引等值查询**只加记录锁，条件里的那条记录之外的间隙没有锁，别人仍可插入新行并被本事务的当前读看到；**二是锁只能锁索引**，若 WHERE 条件里的列没有索引，锁的语义会退化（要么锁全部扫描到的记录与间隙，阻塞过宽；要么无法精确覆盖查询条件对应的范围）；**三是级别被改成 RC** 时间隙锁被显式禁用，只剩外键与重复键检查用得到它，幻读回到必然发生。只有「RR + 范围条件 + 条件列有索引」这一组合，next-key 锁才真正把插入挡在范围之外。

另外，插入本身用的是 **insert intention lock**（插入前在目标间隙上设的一种间隙锁），它使得「同一间隙里不同位置的两个 INSERT」不必互相等待——这也是间隙锁不至于把并发写完全串行化的原因。

## 隔离级别与 binlog 格式的绑定

隔离级别不只影响可见性，它还被复制格式反向约束。官方规则是硬性的：READ COMMITTED 下**只支持行格式（row-based）二进制日志**；若 `binlog_format=MIXED` 却在 RC 下运行，服务器会自动改用 row-based 记录。这条规则本身就是「为什么 ROW 更安全」的官方答案：STATEMENT 格式记录的是 SQL 文本，重放时由副本重新执行，它依赖「副本执行该语句时读到的行集、扫描顺序、以及 NOW()/RAND()/UUID() 这类非确定性函数的结果」与源库一致；RC 下每条 SELECT 都取新快照、且不锁间隙，源与副本极可能命中不同的行集合，于是同一个 UPDATE 改掉的行数都可能不同。像 `UPDATE t SET c=c+1 WHERE ... LIMIT 10`（无 ORDER BY）这种语句，在 STATEMENT 下根本不存在确定性。

ROW 格式记录的是「哪一行、变成什么值」，重放不依赖上下文，因此与隔离级别解耦。代价是日志体积与解析成本，这也是 MIXED 存在的原因：平时用 STATEMENT 省体积，遇到不确定语句自动降级为 ROW。但 MIXED 的判定并不覆盖所有上下文依赖（尤其与 RC 的快照语义叠加时），所以「RC + ROW」是比「RC + MIXED」更可控的组合。相关机制见 [[binlog与增量恢复]]。

## 设置方式与作用域

`SET TRANSACTION ISOLATION LEVEL ...` 有三个作用域，混用是连接池里最常见的配置事故来源：

| 写法 | 生效范围 | 限制 |
| --- | --- | --- |
| `SET GLOBAL TRANSACTION ISOLATION LEVEL ...` | 此后新建的连接 | 需要 `CONNECTION_ADMIN`（或已废弃的 `SUPER`）；已存在的会话不受影响 |
| `SET SESSION TRANSACTION ISOLATION LEVEL ...` | 当前会话随后的所有事务 | 可在事务内执行，但不影响已在执行的那个事务 |
| `SET TRANSACTION ISOLATION LEVEL ...`（不带关键字） | 仅下一个事务 | 不能在事务内执行，否则报 `ERROR 1568 (25001): Transaction characteristics can't be changed while a transaction is in progress` |

服务器默认值也可用启动参数 `--transaction-isolation=REPEATABLE-READ`（注意参数名用短横线，与系统变量 `transaction_isolation` 的下划线形式不同）设置。工程上的判据是：连接池会复用会话，`SET SESSION` 的残留会污染后续业务；要「只对这一段逻辑生效」，应使用不带关键字的写法（只作用于下一个事务）。

## 版本差异（5.7 vs 8.0）

这些默认值变化来自官方「Changes in MySQL 8.0 / Changed Server Defaults」表，逐项都在升级时会产生真实行为差异，不能混着讲：

| 项目 | 5.7 | 8.0 | 实际影响 |
| --- | --- | --- | --- |
| 默认认证插件 | `mysql_native_password` | `caching_sha2_password`（8.0 起取代，只影响新建账户） | 旧客户端报 `Authentication plugin 'caching_sha2_password' is not supported`；该插件账户须走安全连接或 RSA 公钥交换 |
| 默认字符集 / 排序 | `latin1` / `latin1_swedish_ci` | `utf8mb4` / `utf8mb4_0900_ai_ci` | 排序与比较规则变化；索引用字节长度变化 |
| 建用户语句 | `GRANT ... IDENTIFIED BY` 可用（早已弃用） | 8.0.11 移除，改 `CREATE USER` + `GRANT` | 老脚本直接失败 |
| `innodb_autoinc_lock_mode` | `1`（consecutive） | `2`（interleaved） | 批量插入的 ID 连续性与锁粒度变化 |
| `explicit_defaults_for_timestamp` | `OFF` | `ON` | TIMESTAMP 的隐式默认与 NULL 行为变化 |
| `innodb_undo_tablespaces` | `0` | `2` | undo 不再允许放在系统表空间 |
| 读授权表的 DML 加锁 | 会加读锁 | 8.0.22 起不加 | 涉及账号表的并发行为变化 |

另外，5.7 与 8.0 的手册章节编号不同（同一主题在 5.7 常是 14.x，在 8.0 是 17.x），引用时须注明版本，否则回溯会上错页。

## 判据速查

| 你的目标 | 选择 | 代价或注意 |
| --- | --- | --- |
| 高并发短事务、能容忍语句级快照 | READ COMMITTED + ROW 格式 | 幻读可能出现；必须确认 binlog 为 ROW |
| 同一事务内要一个稳定视图（报表、多表核对） | REPEATABLE READ（默认） | 写逻辑必须用当前读，否则更新丢失 |
| 要防住范围插入的幻读 | RR + `FOR UPDATE` + 条件列有索引 | 唯一索引等值查询不锁间隙，仍可能幻读 |
| 强一致、写冲突低 | SERIALIZABLE | 读也持共享锁，吞吐显著下降 |
| 只读快照，不想阻塞任何人 | 显式 `START TRANSACTION WITH CONSISTENT SNAPSHOT` | 只对事务引擎有效，`DROP TABLE` 等 DDL 会破坏它 |
