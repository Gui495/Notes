时序约束是用 Tcl 命令把你对时钟、外部接口时序、例外路径的假设写进工具，让综合与布局布线知道「在这个周期内必须收敛」，而不是让工具按它自己猜的默认假设去优化。

> 📌 来源性质：本页无 raw 素材，依据外部资料编写，待有 raw 素材时再收编。

## 约束文件的分工

同一套时序语义在不同厂商工具里换了名字：

| 格式 | 工具 | 说明 |
|---|---|---|
| `.xdc` | Vivado（Xilinx/AMD） | XDC 是基于 Tcl 的约束格式，语法上是 SDC 的扩展；Vivado 只认 XDC |
| `.sdc` | Quartus（Intel/Altera） | SDC（Synopsys Design Constraints）是业界通用格式，`create_clock` / `set_input_delay` 一套命令原样可用 |
| `.ucf` | ISE（旧版 Xilinx） | 基于文本的约束文件，Vivado 起已被废弃；Spartan-6/7 系列之后不应再出现 |

**判据**：拿到一份工程先看有没有 `create_clock`。没有时钟约束，工具会按时钟「无限快」或按默认周期去优化，此时报告里的 WNS 全是虚假的——它只在工具假设的世界里成立。

**版本差异**：UCF 只存在于 ISE 时代，把 UCF 语法拿去 Vivado 会直接解析失败；同理 Quartus 的 `.sdc` 里常出现只有 TimeQuest 认识的命令（如 `derive_pll_clocks`），不能直接搬到 Vivado。这类差异按工具版本处理，不互相裁决。

## 建立时间与保持时间

先定义两个器件参数（由工艺库给出，与设计无关）：

- **建立时间 $T_{setup}$**：数据必须在时钟有效沿**之前**稳定的最短时间；
- **保持时间 $T_{hold}$**：数据在时钟有效沿**之后**必须继续保持稳定的最短时间。

再把它们变成对路径的约束。一次「发射沿 → 捕获沿」的数据传输，路径延迟由三部分组成：触发器时钟到输出的 $T_{co}$、组合逻辑与布线的 $T_{logic}$、以及捕获端触发器要求的 $T_{setup}$。设时钟周期 $T_{clk}$，两端时钟的不确定性（skew + jitter + 时钟树差异）合并记作 $T_{skew}$：

**建立时间一侧（setup，最长路径）**

$$
T_{clk} \;\ge\; T_{co} + T_{logic,max} + T_{setup} + T_{skew}
$$

含义是：数据必须在下一个捕获沿到达前「提前 $T_{setup}$」就准备好，而时钟本身还有不确定性要扣掉。周期越短（频率越高），留给 $T_{logic,max}$ 的预算越小——这是「提高时钟频率为什么先看组合逻辑深度」的原因。

**保持时间一侧（hold，最短路径）**

$$
T_{co,min} + T_{logic,min} \;\ge\; T_{hold} + T_{skew}
$$

注意这一侧**没有时钟周期**。保持时间违例与频率无关，只与最短路径和时钟树有关，所以「降频」对 hold 违例完全无效——这是初学者最容易搞错的一点。保持时间违例的唯一根治手段是增加该路径的延迟（插 buffer/LUT 延迟）或调整时钟树，不能靠降频。

**判据**：setup 违例随频率升高而恶化、随频率降低而缓解；hold 违例频率无关。看到报告里 hold 为负，先去查时钟树和同一时钟域的短路径，而不是降频。

## slack：把违例量化成一个数

AMD 的时序分析文档给出的定义是直接的：

- **max delay 分析（对应 setup/recovery）**：$\text{slack} = \text{data required time} - \text{data arrival time}$
- **min delay 分析（对应 hold/removal）**：$\text{slack} = \text{data arrival time} - \text{data required time}$

两边都是「余量」的正负号约定不同但含义一致：**slack 为正是还有余量，为负是已经超了 $|slack|$ 的时间**。

两个汇总指标：

- **WNS（Worst Negative Slack）**：所有时序路径中最差的那条 slack。WNS 为正说明最差路径也满足时序；WNS 为负说明至少有一条路径违例。
- **TNS（Total Negative Slack）**：所有违例端点的最差 slack 之和（只累加负值）。WNS 告诉你「最坏有多坏」，TNS 告诉你「总共欠多少」——WNS = −0.01 ns 而 TNS = −500 ns 说明是大量轻微违例（通常是扇出或局部拥塞），WNS = −2 ns 而 TNS = −2 ns 说明就一条路径卡死（通常是超长组合链）。

**判据**：时序收敛的标准是 WNS ≥ 0 且 TNS = 0，而不是「WNS 大于某个小负数就行」。负 slack 意味着工具没有满足你写下的约束，芯片在真实温度电压下大概率出错。

## 时钟约束

时钟是时序分析的基准，所以 `create_clock` 是一切约束的起点。Vivado 的语法（UG903）：

```tcl
create_clock -period 10.000 -name sys_clk -waveform {0.000 5.000} [get_ports clk]
```

要点：

- `-period` 的单位是 **ns**，`10.000` 即 100 MHz；
- `-waveform {上升沿时刻 下降沿时刻}` 用绝对时间描述，默认占空比 50%；非 50% 占空比（如 DDR 的源同步时钟）必须显式写；
- 时钟定义在**端口或引脚**上，工具会自动把它传播到该时钟域内的所有触发器；不需要也不应该给每个寄存器单独写时钟；
- 生成时钟（PLL/MMCM 输出、时钟分频器输出）要用 `create_generated_clock` 而不是再写一个 `create_clock`，否则工具不知道两者的相位关系。

**易错点**：把 `create_clock` 写到内部网络而不是输入端口，导致工具认为该时钟是「内部产生」的，输入端口的时序关系丢失；PLL 输出用 `create_clock` 重定义后，工具会当成两个无关时钟，跨 PLL 的路径全变成未约束。

## 输入输出延迟

FPGA 与外部芯片之间的时序，工具是不知道的，必须由你用 `set_input_delay` / `set_output_delay` 告诉它：

```tcl
# 上游器件在时钟沿后 2.0ns 才把数据送出，最早 0.5ns
set_input_delay -clock sys_clk -max 2.0 [get_ports din]
set_input_delay -clock sys_clk -min 0.5 [get_ports din]

# 下游器件要求数据在时钟沿前 3.0ns 到达
set_output_delay -clock sys_clk -max 3.0 [get_ports dout]
set_output_delay -clock sys_clk -min 0.0 [get_ports dout]
```

机制：这两个约束把「FPGA 引脚」与「外部器件的时序要求」之间的余量折算进内部的 setup/hold 分析中。`-max` 参与建立时间分析，`-min` 参与保持时间分析，所以**只写 `-max` 不写 `-min` 是常见错误**，会让 hold 分析失去外部约束。

**判据**：如果外部器件的数据手册给了 $T_{co}$ 与 $T_{su}/T_h$，那么 `-max` ≈ 上游 $T_{co,max}$ + 走线延迟，`-min` ≈ 上游 $T_{co,min}$；对输出侧则用下游的 $T_{su}$ 折算。数值必须能追溯到器件手册，不能凭感觉填。

## 例外路径：false path 与 multicycle path

这两类约束的本质是**放宽分析**，因此也是「把违例藏起来」的高危操作。

### set_false_path

UG903 的定义是「indicates that a logic path … should not be analyzed」。典型合法场景：

- 异步跨时钟域（CDC）路径：两个时钟没有固定相位关系，工具按最坏情况算必然是负 slack，但真实电路靠同步器保证正确性；
- 静态配置寄存器、只在上电时写一次的寄存器；
- 伪路径（逻辑上不可能同时成立的组合）。

```tcl
set_false_path -from [get_clocks clk_a] -to [get_clocks clk_b]
```

**易错点**：对 CDC 路径 `set_false_path` 只是让工具不再报违例，**不会**自动给你加同步器。如果两个时钟域之间是单 bit 控制信号，必须自己实例化两级触发器同步器；如果是多 bit 数据总线，必须用异步 FIFO 或握手。用 false_path 掩盖一个没做同步的 CDC，是典型的「时序报告全绿、上板随机挂」。

### set_multicycle_path

默认假设是「一个周期内必须到达」。当数据路径确实允许跨多个周期（例如使能信号每 3 个周期才有效一次），可以按多周期约束。UG903 的语法是：

```
set_multicycle_path <path_multiplier> [-setup|-hold] [-start|-end]
                      [-from <startpoints>] [-to <endpoints>] [-through <pins|cells|nets>]
```

默认乘数：setup 为 1，hold 为 0。设置多周期时**必须成对设置**，因为 hold 检查的参照点会跟着 setup 移动：

```tcl
# 允许 2 个周期
set_multicycle_path 2 -setup -from [get_cells src_reg*] -to [get_cells dst_reg*]
set_multicycle_path 1 -hold  -from [get_cells src_reg*] -to [get_cells dst_reg*]
```

两者关系是：**hold 乘数 = setup 乘数 − 1 − hold 缺省偏移**（UG903 表述为 hold 检查发生在 setup 乘数减 1 减 hold 乘数处）。只写 setup 不写 hold 的直接后果是：hold 检查被推到第 2 个沿之前，本来合法的短路径被误判为 hold 违例——这是多周期约束最常见的翻车方式。

**判据**：只有当逻辑上真的存在「每 N 拍才采样一次」的证据（使能信号的周期、状态机的转移条件）时才用 multicycle；把普通路径写成 multicycle 等于把违例推迟到硅片上。

## 怎么读综合后的时序报告

一份 `report_timing_summary` 至少看四个数：

| 指标 | 位置 | 判读 |
|---|---|---|
| WNS | Design Timing Summary 第一行 | < 0 即违例，看绝对值判断严重程度 |
| TNS | 同上 | 反映违例的**总量**，区分「一条卡死」与「一片轻微」 |
| 违例端点数 | 同上 | 数量大 → 结构性问题（扇出/拥塞/约束错误） |
| 逻辑级数（Logic Levels） | 具体路径的 path detail | 级数高（>15~20）说明组合链太长，打拍有效 |

看具体路径时，把延迟拆成 **logic delay** 与 **net delay** 两部分：logic 占大头说明逻辑层级太深，net 占大头说明布线绕远或拥塞。两种情况的修法完全不同。

**判据**：如果 WNS 只差几十 ps 且 TNS 很小，通常是布局布线的随机性，重跑或调 `place_design` 策略即可；如果 WNS 差几百 ps 以上且集中在少数路径，必须改 RTL 结构。

## 三类常见违例与修复

| 原因 | 现象 | 修复 |
|---|---|---|
| 组合逻辑太长 | 逻辑级数高、logic delay 占主导、WNS 与 TNS 同量级 | 插入流水线寄存器打拍（把一级组合拆成两级时序）、retiming、把大位宽运算拆成多周期 |
| 扇出过大 | 单条 net 的 net delay 很大、TNS 大而 WNS 小、违例分散在同一信号驱动的多个端点 | 复制寄存器（`MAX_FANOUT` 属性）、手动插一级缓冲、把控制信号按区域分发 |
| 跨时钟域 | 路径起点终点属于不同时钟域、slack 负得离谱（纳秒级） | 先确认是否真异步：真异步加同步器 + `set_false_path`；有相位关系则用 `create_generated_clock` 正确建模 |

补充手段：

- **流水线打拍**是最通用的修复。每插一级寄存器，组合延迟被切成两段，代价是增加一个周期的延迟（latency）。对吞吐量敏感而对延迟不敏感的流水线设计，这是首选。
- **`(* keep = "true" *)`**：告诉综合器不要把这个信号/寄存器优化掉。用途是保留用于调试的观测点、保留跨模块的中间信号。注意它的作用域只到综合——布局布线阶段仍可能被优化，需要更强的 `DONT_TOUCH`（Vivado 的 `set_property DONT_TOUCH true`）来阻止实现阶段改动。
- **不要让 keep 变成「强行保留坏结构」**：被 keep 住的逻辑照样参与时序分析，保留一个高扇出信号只会让违例更严重。

**版本差异**：`(* keep *)` 在旧版 XST 里可以省略 `= "true"`，Vivado 推荐写全 `(* keep = "true" *)`；`DONT_TOUCH` 是 Vivado 实现阶段的属性，与综合属性 `KEEP` 不是一回事。这类写法差异按工具版本查对应手册，不跨版本套用。

## 关联

- [[FPGA]]：时序约束是 FPGA 流程里「综合之后、上板之前」的必经环节，本页补的是点灯教程之外的分析方法。
- [[引脚约束与位流]]：引脚约束管「信号接到哪个管脚」，时序约束管「信号在多少 ns 内到达」，两者常写在同一个 XDC 里但语义完全不同。
- [[Verilog模块]]：违例的根因大多在模块内部的组合逻辑组织方式，约束只是把问题显式化。
- [[RTL设计与Testbench]]：约束写错（比如 clock 定义在内部网络）属于设计错误而非仿真错误，仿真通过不代表时序收敛。
- [[阻塞与非阻塞赋值]]：非阻塞赋值保证触发器行为与「时钟沿采样」的时序模型一致，是时序分析能成立的语言层前提。
