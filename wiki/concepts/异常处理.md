异常处理是 Java 用 `Throwable` 体系把「正常路径」与「错误路径」分离、并用受检异常在编译期强迫调用方表态的一套机制。

> 📌 来源性质：本页无 raw 素材，依据外部资料编写，待有 raw 素材时再收编。

## Throwable 的三层结构

`Throwable` 之下分两支：`Error` 与 `Exception`。`Error` 表示系统级严重错误——Oracle 教程的说法是它们「normally used for serious, hard errors in the system, such as those that prevent the JVM from running」，程序通常不应捕获；`Exception` 才是应用代码处理的对象。

`Exception` 内部再按是否受检分裂，判据只有一条：受检异常是「除 `Error`、`RuntimeException` 及其子类之外的所有异常」，`Error` 与 `RuntimeException` 的两支合称非受检异常（unchecked）。由此得到三条实践判据：

| 分支 | 典型代表 | 编译器是否强制处理 | 处理策略 |
| --- | --- | --- | --- |
| `Error` | `OutOfMemoryError`、`StackOverflowError` | 否 | 一般不捕获，让进程暴露问题 |
| `RuntimeException` 及其子类 | `NullPointerException`、`IllegalArgumentException`、`ClassCastException` | 否 | 属于编程错误，修代码而非 catch |
| 其它 `Exception` | `IOException`、`SQLException`、`InterruptedException` | 是，必须 try-catch 或 `throws` 声明 | 处理、包装上抛、或交给上层 |

容易记错的是 `InterruptedException`：它继承 `Exception` 而不是 `RuntimeException`，因此是受检异常。关于「要不要扩大使用非受检异常」是长期的设计争论，教程单列了 Unchecked Exceptions — The Controversy 一节讨论两种立场，本页不裁决。

## try-catch-finally 的执行顺序

`finally` 的语义是「只要 `try` 退出就会执行」——教程用词是 always，并明确它存在的理由之一就是防止清理代码被 `return`、`continue`、`break` 绕过。唯一的豁免是 JVM 在 `try` 或 `catch` 执行期间退出。

执行顺序按 `try` 的三种出口展开：正常结束则直接进 `finally`；抛出异常且被某个 `catch` 匹配，则执行该 `catch` 体再进 `finally`；抛出异常却无人匹配，则先执行 `finally`、再把异常向上抛。多个 `catch` 自上而下匹配第一个相容类型，因此子类 `catch` 必须写在父类之前，否则父类分支会把它遮住、编译器按不可达代码报错（JLS 对 catch 可达性的规则，本页未抓取原文，待核）。

`return` 与 `finally` 的交界是最容易出错的地方，分两条：`try` 中写 `return` 时 `finally` 仍会执行，这正是它「防止清理被绕过」的价值；但若 `finally` 自己也 `return` 或 `throw`，就会覆盖 `try` 的返回值或异常——按 JLS §14.20.2 的规则，`finally` 块 abruptly 完成时整个 `try` 语句以同一原因 abruptly 完成，所以 `try` 里算好的返回值被丢弃（该节原文本页未逐字抓取，按规范条目引用，待核）。由此得到两条纪律：不要在 `finally` 里 `return`；`finally` 只做释放资源一类不会失败的动作。

`finally` 里对局部变量的修改也不会改变已经算出的返回值，因为返回值在进入 `finally` 之前就已确定（同上，属 JLS §14.20.2 语义的推论）。

## try-with-resources 与 AutoCloseable

任何实现 `java.lang.AutoCloseable` 的对象都可以写进 `try (...)` 的资源头，`close()` 会在退出该语句时被自动调用；`java.io.Closeable` 是它的子接口，所以所有 IO 流天然可用。`AutoCloseable` 的文档把动机写得很直白：及时释放（prompt release），避免资源耗尽异常。资源自 Java 7 起可用（`AutoCloseable` 的 Since 标记为 1.7），在此之前只能靠 `finally` 手工 `close()`，而手工写法里 `close()` 自身抛异常会让前一个资源泄漏。

三条判据值得记牢。多个资源按声明顺序创建、按**相反顺序**关闭。`catch` 与 `finally` 都在资源关闭**之后**才执行。`try` 体与 `close()` 同时抛异常时，`try` 体的异常成为主异常，`close()` 的异常被抑制（suppressed），可用 `Throwable.getSuppressed()` 取回；手工 `finally` 写法的结果正好相反——`finally` 抛出的异常胜出，`try` 的异常被吞掉，这也是教程推荐 try-with-resources 的核心理由之一。

接口本身的设计约束也影响实现：`AutoCloseable.close()` 声明 `throws Exception`，文档强烈建议实现类收窄为更具体的异常、或在不失败时干脆不抛；并明确建议不要把 `close()` 写成抛 `InterruptedException`——它和线程中断状态交互，且一旦被抑制就可能引发难以定位的运行期行为。另外 `AutoCloseable.close()` 不要求幂等，`Closeable.close()` 则要求重复调用无副作用，两者不能混。

Java 9 之后还允许把「事实上不再赋值」的已有变量直接放进资源头（JEP 213 的改动），本页未展开，待核细节。

## 异常链

包装上抛时不能丢掉根因，否则栈里只剩最后一层。`Throwable` 为此提供了构造器 `Throwable(String, Throwable)`、`Throwable(Throwable)` 与方法 `getCause()`、`initCause(Throwable)`；典型写法是 catch 到 `IOException` 后 `throw new SampleException("Other IOException", e)`，把 e 挂成 cause 再抛。`initCause` 只能设置一次，重复调用抛 `IllegalStateException`（`Throwable` 规范条目，本页未抓取原文，待核）。默认的 `printStackTrace()` 会把整条 cause 链按 `Caused by:` 逐层打出，所以「有没有挂 cause」直接决定了排查时能不能看到原始失败点。

同时 `getStackTrace()` 返回 `StackTraceElement[]`，可以自定格式输出文件名、行号、方法名——需要把异常写进日志或响应体时用它，而不是依赖默认输出。

## 自定义异常

教程给出的自定义判据是四个问题：平台是否已有可表达该语义的异常类型；是否需要让使用者把你的异常与其它厂商的异常区分开；你的代码是否抛出多个**相关**异常需要被一起捕获；接口的使用者能否访问到你借用的第三方异常类型。四条中任一为「是」，就该自带异常类。

父类选择只看是否要强制调用方处理：继承 `Exception` 即受检，调用方必须 catch 或声明；继承 `RuntimeException` 则不强制。教程的链表示例选了 `Exception` 作父类，理由是其它既有子类要么过于专用、要么与 `LinkedListException` 无关。命名上教程建议统一以 `Exception` 结尾。自定义异常至少要提供「消息 + cause」的构造器，否则包装时必然丢根因。

## 受检异常的传染性与吞异常反模式

受检异常具有传染性：一个方法声明 `throws IOException`，它的每个调用者要么 catch，要么也跟着声明，直到某一层真正处理掉，或者一路传到 `main`。这是编译期检查的代价——API 签名被迫暴露实现细节，也是很多人改用 `RuntimeException` 包装的动机。JLS §11.2 规定，若方法体可能抛出受检异常 E 而 E 不是该方法 `throws` 子句所列类型的子类型，编译即失败（该节原文本页未逐字抓取，按规范条目引用，待核）。

由此衍生出几类常见反模式，判据都是「错误信息是否还在」。空 `catch {}` 是最直接的吞异常；`catch (Exception e) { log(e); }` 只记日志不重抛、不降级，等于把失败变成了「看起来成功」；`catch (Exception e)` 一把抓还会让受检检查失效，把本可在编译期发现的遗漏拖到运行期；在 `finally` 里 `return` 或用返回值表示失败（返回 `null`、`-1`、空集合）则会掩盖异常本身。

正确的处置只有三种：就地处理（能恢复、能降级，并说明后果）；包装成有业务语义的异常、带上 cause 再抛；直接声明 `throws` 把决定权交给上层。除此之外的「处理」大多只是让异常消失。这一点与 [[IO流]] 里资源关闭的写法、[[多线程]] 里 `InterruptedException` 的处理是同一条原则的三个侧面。
